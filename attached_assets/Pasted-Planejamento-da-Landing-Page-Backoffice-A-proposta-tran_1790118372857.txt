Planejamento da Landing Page + Backoffice
A proposta é transformar a landing page em uma central de doações direcionadas, onde o visitante escolhe exatamente qual necessidade deseja apoiar, visualiza o progresso daquela meta e posteriormente pode consultar a prestação de contas.

O fluxo principal será:

Visitante acessa a página;
Escolhe uma ação;
Visualiza a finalidade da arrecadação;
Seleciona um valor pré-definido;
Realiza a doação;
Acompanha o progresso da meta;
Consulta a prestação de contas pelo Portal da Transparência.
Para produção, CPF, comprovantes e informações de beneficiários devem ser tratados com controle de acesso, anonimização e revisão jurídica conforme a LGPD. Comprovantes também podem conter nome, endereço, banco, agência e número de conta, portanto não devem ser publicados sem redaction adequada.

Protótipo funcional da landing page
O código abaixo cria uma primeira versão visual com:

Hero focado em doação;
Ações com metas individuais;
Valores pré-definidos por ação;
Barra de progresso;
Modal de doação;
Portal da Transparência;
CPF mascarado para demonstração;
Área de comprovantes;
Botão de gamificação preparado para receber a lógica futura;
Layout responsivo;
Navegação externa eliminada.
Salve como index.html.

Estrutura recomendada do backoffice
O painel administrativo deve ser separado da landing page, por exemplo:

site público: divulgação e conversão;
painel.incesc.org.br: administração interna;
API: regras, autenticação, pagamentos e transparência;
armazenamento privado: comprovantes originais;
armazenamento público: comprovantes revisados e anonimizados.
Módulos do painel
1. Dashboard
Exibir:

Total arrecadado;
Total de doações;
Ações ativas;
Ações concluídas;
Pagamentos pendentes;
Comprovantes aguardando revisão;
Valor arrecadado por período;
Progresso das metas;
Últimas atividades administrativas.
2. Gestão de ações
Campos recomendados:

Título;
Categoria;
Descrição pública;
Descrição interna;
Meta financeira;
Valores pré-definidos;
Imagem;
Data de início;
Data de encerramento;
Status;
Responsável interno;
Critério de conclusão;
Exibição pública;
Ordem de apresentação.
Status possíveis:

Rascunho;
Aguardando aprovação;
Publicada;
Em arrecadação;
Meta atingida;
Em execução;
Concluída;
Arquivada.
3. Gestão de doações
A administração deve conseguir consultar:

Identificador da doação;
Ação relacionada;
Valor;
Data;
Status do pagamento;
Meio de pagamento;
Identificador externo do gateway;
Nome do doador, caso autorizado;
E-mail, caso autorizado;
Consentimento para comunicação;
Estorno ou cancelamento.
O painel não deve exibir dados completos de cartão. O processamento deve ocorrer por um provedor especializado.

4. Gestão de despesas
Cada despesa deve estar vinculada a uma ação.

Campos:

Ação;
Categoria da despesa;
Descrição;
Valor;
Data de pagamento;
Beneficiário ou fornecedor;
CPF ou CNPJ armazenado de forma protegida;
Comprovante original;
Comprovante público revisado;
Status de aprovação;
Responsável pelo lançamento;
Observações internas.
5. Portal da Transparência
O administrador deverá poder publicar:

Ação relacionada;
Valor arrecadado;
Valor utilizado;
Saldo;
Descrição da aplicação;
Data;
Status;
Comprovante revisado;
CPF mascarado, quando a exibição for realmente necessária;
Informação sobre proteção de dados.
O ideal é não exibir CPF do beneficiário por padrão. Mesmo mascarado, ele pode contribuir para identificação quando combinado com outras informações.

Uma exibição mais segura seria:

Beneficiário protegido por privacidade. Documento validado internamente.

Quando houver necessidade de exibição:

CPF: ..*-42

O CPF completo deve permanecer apenas no ambiente interno, com acesso restrito.

7. Gamificação
A área pode começar com uma estrutura simples:

Perfil do apoiador;
Histórico de contribuições;
Badges;
Níveis de participação;
Metas coletivas;
Campanhas especiais;

Compartilhamento de conquistas.
Regras importantes:

Não publicar valores doados sem consentimento;
Não mostrar dados de beneficiários;
Não criar ranking que constranja apoiadores;
Permitir participação anônima;
Separar gamificação de qualquer benefício assistencial;
Registrar consentimento para compartilhamento social.

CREATE TABLE users (
  id UUID PRIMARY KEY,
  name VARCHAR(150) NOT NULL,
  email VARCHAR(180) UNIQUE NOT NULL,
  password_hash TEXT NOT NULL,
  role VARCHAR(40) NOT NULL,
  active BOOLEAN DEFAULT TRUE,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE donation_actions (
  id UUID PRIMARY KEY,
  title VARCHAR(180) NOT NULL,
  slug VARCHAR(180) UNIQUE NOT NULL,
  category VARCHAR(80) NOT NULL,
  public_description TEXT NOT NULL,
  internal_description TEXT,
  goal_amount DECIMAL(12, 2) NOT NULL,
  raised_amount DECIMAL(12, 2) NOT NULL DEFAULT 0,
  suggested_values JSONB NOT NULL,
  image_url TEXT,
  status VARCHAR(40) NOT NULL DEFAULT 'draft',
  starts_at TIMESTAMP,
  ends_at TIMESTAMP,
  created_by UUID REFERENCES users(id),
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE donations (
  id UUID PRIMARY KEY,
  action_id UUID NOT NULL REFERENCES donation_actions(id),
  amount DECIMAL(12, 2) NOT NULL,
  payment_method VARCHAR(40) NOT NULL,
  payment_status VARCHAR(40) NOT NULL,
  gateway_transaction_id VARCHAR(180),
  donor_name VARCHAR(150),
  donor_email VARCHAR(180),
  donor_document_encrypted TEXT,
  anonymous BOOLEAN DEFAULT TRUE,
  communication_consent BOOLEAN DEFAULT FALSE,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE expenses (
  id UUID PRIMARY KEY,
  action_id UUID NOT NULL REFERENCES donation_actions(id),
  description TEXT NOT NULL,
  category VARCHAR(100) NOT NULL,
  amount DECIMAL(12, 2) NOT NULL,
  paid_at DATE,
  beneficiary_name VARCHAR(180),
  beneficiary_document_encrypted TEXT,
  status VARCHAR(40) NOT NULL DEFAULT 'pending_review',
  internal_receipt_url TEXT,
  public_receipt_url TEXT,
  public_description TEXT,
  approved_by UUID REFERENCES users(id),
  published_by UUID REFERENCES users(id),
  created_by UUID REFERENCES users(id),
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE audit_logs (
  id UUID PRIMARY KEY,
  user_id UUID REFERENCES users(id),
  entity_type VARCHAR(80) NOT NULL,
  entity_id UUID NOT NULL,
  action VARCHAR(80) NOT NULL,
  metadata JSONB,
  ip_address INET,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
Os campos donor_document_encrypted e beneficiary_document_encrypted devem ser criptografados. Não é recomendado guardar CPF em texto puro.

Fluxo de publicação de uma despesa
text
Copiar

1. Administrador cadastra a ação
2. A ação é aprovada e publicada
3. Doações são recebidas
4. Sistema atualiza a arrecadação
5. Responsável cadastra a despesa
6. Comprovante original é armazenado em área privada
7. Responsável remove dados sensíveis do comprovante
8. Segundo usuário revisa a documentação
9. Sistema publica a versão revisada
10. Portal da Transparência exibe a despesa
11. Log registra quem cadastrou, aprovou e publicou
Pontos críticos antes da publicação
Usar imagens e logotipo oficiais do INCESC;
Substituir os dados fictícios do protótipo;
Definir oficialmente as metas de cada ação;
Confirmar a chave Pix ou gateway de pagamento;
Criar política de privacidade;
Criar termo de consentimento para doadores;
Definir prazo de retenção dos dados;
Revisar comprovantes antes da publicação;
Não expor dados bancários;
Não publicar CPF completo;
Não publicar dados de crianças ou pessoas vulneráveis;
Criar backup dos comprovantes;
Registrar logs de todas as alterações;
Ativar autenticação em dois fatores no backoffice;
Usar HTTPS;
Fazer validação dos valores também no backend;
Impedir que o frontend altere diretamente metas ou arrecadações
